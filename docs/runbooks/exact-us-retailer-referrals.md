# Exact US retailer referrals (cohort A)

The pilot adds the two reviewed shades of the cohort A brand product from its two reviewed retailers to the existing brand product group. The cohort, its retailers, listings and native shade pairs are defined in [`config/reviewed_retailer_cohorts.json`](../../config/reviewed_retailer_cohorts.json) under `cohort_a`. The application flag named there as `cohort_a.flag` defaults to off. The pilot offers named US shades through `get_offers` with signed links to the retailer PDP.

## Deploy and canary

1. Deploy the merged backend through the normal production workflow with the pilot flag off. Check the actual web and worker revisions. Check the image used by any job that can rebuild these PDPs or write retailer listings. The current [job image tool](../../infra/gcp/reimage_jobs.sh) can plan and verify named job updates.
2. On the deployed image, run the cohort A refresh module (`scripts/ops/` script whose `scope` is `cohort_a.refresh.scope`) with `plan` from a dedicated US crawl-subnet Cloud Run job whose name starts with `cohort_a.refresh.job_prefix`. Use the production Cloud SQL secret, `PIVOTA_ENV=production`, `GOOGLE_CLOUD_PROJECT=<PROD_PROJECT>`, the env var named by `cohort_a.refresh.release_commit_env` set to the image commit. The job needs no database pin variables: the host and database its `DATABASE_URL` names, and the server it reaches, must hash to the sha256 pins in `scripts/ops/reviewed_job_pins.py`, or it holds before any write and reports only the mismatched digests. Set the current enrichment identity and variant-barcode flags for the job. Confirm the existing canonical group and the two observed seller identities, the signed-link domain policy, and exactly two native variants per seller.
3. Run the same job with `apply` and the write flag named by `cohort_a.refresh.write_flag` set to `1`. Save the output with the four offer IDs. Replay against the same scope and verify the keys, seller ownership, native shade and currency. A fresh out-of-stock observation may remove that offer from results. The job preserves the existing brand product and checks its original SKU, offer, index, and PDP snapshots around each write.
4. Enable the pilot flag on the reviewed backend web revision for the four rows. Call the existing production MCP `get_offers` for each canonical shade with `market=US`. Compare offer results and signed redirects against fresh Shopify source reads. Exercise an unnamed shade, a non-US request, and an unrelated listing. Verify that a standard PDP refresh preserves the brand page and that the named retailer offers remain referral-only.

## Refresh and rollback

Run `refresh` using the same reviewed image, job identity, network, production database and write switch after the canary apply. It requires all four existing offer keys. Each refresh checks the storefront product, native variant, UPC, explicit US currency, observed stock and price. Unconfirmed observations leave stored facts alone. The reader serves a proof for at most four hours from the storefront read. Run the scoped job hourly and monitor its completion and the age of the oldest of the four stored proofs.

Disable the web pilot flag and pause the dedicated refresh trigger to withdraw the pilot. The ordinary catalog, PDP assembler and cart reader exclude reviewed retailer offers independently of the serving flag. Existing signed links still point to their particular retailer shade.

The cohort B refresh job uses the same pins plus a sha256 pin on the Shopify shop id its storefront returns; the six-shade expansion job also pins its runtime service account per environment. None of them needs extra environment variables.

## Cohort C US referrals

Supply the versioned cohort C manifest through the controller's private ops bundle. Set `REVIEWED_RETAILER_MANIFEST_PATH` to its mounted file and `REVIEWED_RETAILER_MANIFEST_SHA256` to the reviewed digest in every catalog-serving and ingestion runtime that handles this cohort. With both settings and the write and serving switches unset, cohort C is absent. Invalid settings or enabled switches without a manifest stop startup. Keep the verified manifest mounted while any of the cohort's rows exist, including while serving is disabled, so the ordinary offer, PDP, intake and checkout routes continue to reserve the listing.

The reader accepts a named US request for the pinned canonical product and one of the eight canonical variant IDs. It returns a signed variant-specific redirect only when the native variant and GTIN still match the canonical SKU and the observed retailer proof is current. The controller starts with `REVIEWED_RETAILER_EXACT_ENABLED` off. Before the initial apply, verify the seller attribution and exact eight offers in a read-only production plan and obtain the approved one-off window. Use `apply_reviewed_retailer` with `RETAILER_COHORT_C` in a serializable transaction. It reads and locks the existing observed seller and verifies the seller, canonical product, index, and seed are preserved. Reconfirm the eight approved keys and verify the no-op replay. After the serving switch is enabled, verify all eight signed destinations via the production MCP, including unreviewed, merchant-scoped and non-US negative controls.

Run `python -m scripts.ops.reviewed_retailer_offers plan` for a complete existing cohort. The module pins the production database and reviewed backend image with `REVIEWED_RETAILER_C_RELEASE_COMMIT` and checks the dedicated `reviewed-retailer-c-us-` job prefix. The `refresh` mode also requires `REVIEWED_RETAILER_REFRESH_WRITE_ENABLED=1`. The job validates the product, vendor, retailer SKUs, GTINs and explicit US presentment before refreshing prices and stock in one transaction. The four-hour proof expiry withholds stale offers. To withdraw, disable cohort serving and pause its refresh trigger. The controller can remove the manifest after rollback verifies removal of the scoped data.
